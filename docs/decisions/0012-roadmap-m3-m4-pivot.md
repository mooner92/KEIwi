# 0012. 로드맵 조정 — M3 Overview 흡수 · M4 보류 · M1/M2 고도화 우선

- 상태: 채택 (2026-06-28, 사용자 결정)
- 영향: [Constitution.md](../../Constitution.md) §마일스톤(M3/M4) 및 [README](../../README.md) 마일스톤표를 **개정**한다(헌장 로드맵 절은 이 ADR로 갱신).

## 맥락

M1(메트릭)·M2(로그)가 라이브된 뒤 M3(여유 리소스)·M4(장애 추적)의 필요성과 형태를 재검토했다.

- **Overview가 이미 리소스 메트릭을 보여준다** — 플릿 상태 카드 + 노드별 시스템/GPU 메트릭(Grafana 임베드, 드릴다운). M3 "여유 리소스"와 **데이터원이 같고**(M1 Prometheus/DCGM) 둘 다 "서버 상태"라, 별도 탭은 중복·혼란.
- **M4 정식 incident 추적**(수동 기록·포스트모템·타임라인)은 **5서버 연구 플릿엔 과하다**(엔터프라이즈용). 실용 니즈("문제를 보고 추적")는 M2 신호 우선 뷰([ADR-0011](0011-signal-first-log-ux.md))로 대부분 충족.
- 사용자 판단: *"M3/M4 필요성을 크게 못 느낀다. M1·M2를 더 고도화해 해결할 수 있을 것 같다."*

## 결정

**(1) M3(여유 리소스)을 Overview에 흡수.** 별도 Resources 탭을 두지 않고 **Overview를 "여유 리소스" 뷰로 확장**한다 — 플릿 현황 + `free/busy/full` 판정 + 작업 배치 추천. 새 수집 없이 **M1 메트릭 재사용**(CPU idle·mem available·GPU util/free VRAM에서 판정 파생). 제품 비전("어느 서버가 여유 있는지 → 작업 배치")은 Overview 확장으로 추구. → 이는 **새 마일스톤이 아니라 M1 고도화**.

**(2) M4(Incidents) 보류.** 정식 장애 추적 시스템은 만들지 않는다. 실용 니즈는 M2 신호 우선 뷰 + (필요 시) Grafana annotation + 향후 M5 알림으로 충족. Incidents 탭은 당장 제거하지 않고 placeholder 유지(필요해지면 재검토).

**(3) 다음 착수 = M1/M2 고도화.** 새 마일스톤(M3 신탭/M5) 착수보다 **기존 M1·M2를 심화**한다. M5(알림)의 가치(push·책임자 귀속)는 인정하나 우선순위는 M1/M2 심화 이후. 후보 백로그는 [README](../../README.md) 또는 M1/M2 tasks 백로그에 둔다.

## 고려한 대안

- **원안 5마일스톤(M3 신탭·M4 정식·M5) 유지** — 탭 중복(M3↔Overview)·규모 과설계(M4) → 기각.
- **M5(알림) 먼저** — 새 가치이나 사용자가 "M1/M2 심화 우선"을 선택 → 후순위로.
- **Overview·Resources 2탭 분리 유지** — 역할 구분 가능하나 데이터원 동일·UX 중복 → 흡수가 단순(§6 지루한 기술/단순성).

## 결과

- 탭 지향: **Overview(여유 리소스 포함) · Logs** 중심. Resources 탭은 Overview 확장 시 제거, Incidents는 보류 placeholder.
- M3의 제품가치(작업 배치)는 살아있되 **M1 고도화로 실현**(별도 마일스톤 폐지).
- M4는 사실상 폐지(경량 annotation 옵션만 잔존).
- 다음 작업은 M1/M2 고도화 백로그에서 선택(예: Overview 여유 리소스 뷰, 메트릭↔로그 드릴다운, 모델↔GPU 매핑 노출, data01~03 확장, 경량 Grafana 알림).
- 헌장 §마일스톤·README 마일스톤표는 본 ADR 기준으로 갱신.
