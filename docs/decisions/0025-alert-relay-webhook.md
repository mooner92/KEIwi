# 0025 — 웹훅 중계(alert-relay) 도입: "스레딩은 값어치 없다" 판단의 갱신

- 상태: 채택(2026-08-03) — **단, 실채널 컷오버는 섀도 2주 게이트 통과 후**(T-E3-7)
- 맥락: [specs/alert-enrichment §3](../../specs/alert-enrichment/spec.md) · 헌장 §11(에이전트 생성/사람 적용) · §12(라이브 직접수정 금지) · §13(시크릿 레포 밖) · §15(알림 노이즈 최소화)
- 관련: `infra/alert-relay/` · `docs/runbooks/alert-relay-rollback.md` · [ADR-0014](./0014-log-assistant.md)(어시스턴트 동시 1) · [ADR-0015](./0015-assistant-exploratory-query.md)

## 맥락 — 뒤집는 판단 1건

`contact-points.yaml:19-20`은 이렇게 적혀 있었다:

> 정말 스레딩이 필요해지면 webhook 수신처 + fingerprint→thread_ts 중계 서비스가 필요한데,
> **5노드 규모에 그 인프라를 더할 만한 값어치는 아직 없다.**

2026-08-03 첫 실전 알림(DiskUsageHigh · data04)이 이 판단의 전제를 바꿨다. 알림은
정확히 발화했지만, 사람이 **30분 동안 df→du→find→소유자**를 손으로 추적했다. 그때
드러난 요구는 "스레딩"이 아니라 다음 셋이었다:

- (c) 알림에 **분석**을 붙여라 — 로컬 vLLM은 이미 있다(`POST :3105/api/assistant`).
- (d) **누가·언제·어떤 의도로**를 붙여라 — 파일시스템 증거와 journald `COMMAND=`는 이미 있다.
- (e) **발생과 해결이 한 덩어리로** 보여야 한다.

실측된 제약: Grafana 13의 Slack 알림기에는 `thread_ts` 옵션이 **없다**
(`/api/alert-notifiers` 확인). 즉 Grafana가 메시지를 보내는 한 스레드도, 후속 답글도 불가능하다.

## 결정

**Grafana webhook을 받아 Slack에 직접 게시하는 소형 중계(`alert-relay`)를 만든다.**
중계가 원 메시지를 게시하면 응답으로 `ts`를 쥐고, 같은 bot token으로 `thread_ts`만
넘기면 스레드 답글이 된다(추가 스코프 불필요).

판단이 뒤집힌 지점은 정확히 하나다: **중계의 값어치를 "스레딩"으로만 계산한 것이 틀렸다.**
같은 컴포넌트 하나가 ① 스레딩 ② LLM 분석 답글 ③ 귀속 요약 답글 ④ 발생→해결 한 스레드를
전부 해결한다. 하나의 값어치로는 부족했지만 넷의 합은 충분하다.

구현 계약(spec §3.2·§3.3):

| 항목 | 결정 |
| --- | --- |
| 언어 | Python 3 **stdlib 전용**, pip 0개 — egress 최소·감사 용이·1인 유지보수 |
| 위치 | data05 · systemd(`Restart=always`) · `:8130` · `POST /webhook`·`GET /healthz` |
| 동기 경로 | 시크릿 검증 → `chat.postMessage` → sqlite 저장 → 200. **LLM 없음** |
| 비동기 | ① E4 결정적 수집 답글 ② 어시스턴트 답글. 실패는 **조용히 생략**(Slack 도배 금지) |
| 포맷 정본 | payload의 렌더된 `title`/`message` **그대로** — E1 템플릿 한 곳 |
| 반출 | `build_slack_payload()` **단일 함수**만이 Slack으로 나가고 전부 redaction 통과 |

### 보강 결정 2건 [2026-08-04, 적대적 검증 뒤]

**① 멱등은 디스크가 아니라 메모리에 둔다.**
실증된 사고: DB가 쓰기 불가일 때 `store.remember`가 게시 **뒤에** 예외를 던졌고 `do_POST`가
그걸 안 잡아 Grafana에 **응답이 아예 가지 않았다**. Grafana는 재시도했고 재시도마다 Slack
최상위 게시가 하나씩 늘었다 — 알림 1건에 게시 3건. 하필 이 실패의 대표 원인이 **디스크 풀**이고
relay의 주 용도가 **DiskUsageHigh**다.

선택지는 둘이었다.

| 안 | 내용 | 판정 |
| --- | --- | --- |
| 게시 **전** sqlite 예약(멱등키 INSERT) | 중복은 완벽히 막힌다 | ❌ **기각** — 디스크가 차면 예약이 실패해 **알림이 통째로 사라진다.** "디스크가 찼다"고 알려야 할 바로 그때 알림이 죽는 자기모순. 전달 무손실(§3.2-1)이 상위 계약이다 |
| 게시 **후** 저장 실패 흡수 + **메모리 원장**으로 중복 차단 | 예약이 절대 실패하지 않는 매체에 있다 | ✅ **채택** |

받아들인 손실은 명시한다: **relay 재시작 직후 수 초의 재시도는 중복 게시가 될 수 있다.**
반대편(디스크 장애 시 알림 소실)보다 가볍다는 판단이다. 창(`RELAY_DEDUP_WINDOW_SEC`, 기본
300초)이 **재시도(수십 초)** 와 **재통지(`repeat_interval` 4~12h)** 를 시간으로 가른다.
함께 고정한 계약 2개: 저장소는 예외를 올리지 않고 메모리 티어로 계속한다(`degraded`가
`/healthz` 503으로 나간다) · `do_POST`는 **어떤 예외에도 응답을 낸다**.

**② 반출 세탁은 E3·E4가 같은 파일을 쓴다**(`infra/alert-relay/keiwi_redaction.py`).
방어가 두 벌이던 동안 relay 쪽이 4종에서 더 약했다 — URL을 빼돌린 뒤 호스트 검사 없이 복원 ·
`~/` 미처리 · 허용목록 밖 절대경로 통과 · 하드 거부 부재. **같은 위협이면 같은 방어**이고,
복제는 "한쪽만 고쳐지는 미래"를 산다. 게이트 P6이 "같은 객체인가"를 기계로 본다.
예외 하나: **1차 전달**만 하드 거부 시 폴백 본문으로 대체한다 — 답글은 없어도 되지만
알림은 없으면 안 되기 때문이다.

## 트레이드오프 — 정직하게: 알림 경로가 relay에 의존하게 된다

컷오버 후 relay가 죽으면 Slack 알림이 멈춘다. 이것은 "전달은 어떤 부가 시스템에도
의존하지 않는다"는 제약과 **긴장 관계이고, 그 긴장은 없어지지 않는다.**

판단의 근거: **LLM 의존(금지)과 소형 결정적 중계 의존(관리 가능)은 다르다.** LLM은
지연·품질·가용성이 모두 비결정적이지만, 중계는 ~800줄 stdlib 코드에 상태가 sqlite 한 개다.
업계도 알림 게시 주체가 중계인 구조를 표준으로 쓴다(Robusta OSS: 알림 선게시 → 조사 결과는
스레드 답글). 대신 **4중 완화를 의무**로 한다:

1. **섀도 2주** — 기존 직송을 건드리지 않고 relay는 `#keiwi-relay-test`에만 게시. 실채널 무영향.
2. **감시** — external-watchdog에 `/healthz` 등록(감시자를 감시하는 기존 축).
3. **롤백 1파일** — `infra/monitoring/grafana/rollback/contact-points.fallback.yaml` 복사 + 리로드(<5분).
   **컷오버 전에 리허설한다**(AC-E3-6).
4. **소형 유지** — stdlib 전용·자율 루프 없음. 커지면 그 자체가 되돌리기 신호다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| **A. 현행 유지(직송만)** | 요구 (c)(d)(e) 중 어느 것도 풀리지 않는다. 30분 수동 추적이 그대로 남는다 |
| **B. 직송 유지 + 보강만 별도 채널** | 알림과 분석이 서로 다른 메시지로 흩어져 상관이 사람 머릿속에만 남는다. 다만 **롤백 시 유력한 대안**이라 런북 §6에 남겨 둔다 |
| **C. Grafana에 스레딩 패치/플러그인** | 업스트림 의존·업그레이드마다 재확인. 5노드 규모에 과잉 |
| **D. HolmesGPT/Robusta 통짜 도입** | 5노드·1인 규모에 과잉이고 egress·의존성이 늘어난다. **구조만 차용**한다 |
| **E. LLM을 동기 경로에** | 전달이 GPU 가용성에 묶인다. 헌장 위반이자 §3.4 완화의 전제를 부순다 |

## 되돌리기 조건 (이 ADR의 유효기간)

다음 중 **하나라도** 성립하면 직송으로 되돌린다(`docs/runbooks/alert-relay-rollback.md`):

1. 섀도 2주 게이트 실패 — 중계 유실 ≥1건 · 기본 게시 지연 p95 ≥5s · 2차 답글이 유용하지 않다(사람 판정).
2. 컷오버 후 relay 원인의 알림 유실이 **1건이라도** 발생.
3. 같은 원인으로 **2회 이상** 롤백 — 임계나 재시도를 만지지 말고 구조(대안 B)를 다시 본다.
4. 유지 부담이 편익을 넘었다고 판단될 때(코드가 커지거나, 한 달에 한 번 이상 손이 갈 때).

되돌린 이유·시각을 이 문서 하단에 남긴다. 남기지 않으면 다음 사람이 같은 실험을 반복한다.

## 결과 (예상 · 섀도에서 실측으로 대체할 것)

- 알림 도착 즉시: 현재값·마운트·시작시각·딥링크(E1·E2가 이미 제공).
- +수 초: 귀속 요약(누가·무엇을·얼마나 — 계정명·카테고리까지, 원문 경로·명령은 반출 금지).
- +1~3분: 근거 번호가 붙은 LLM 해석. **조치는 자동 적용하지 않는다 — 출발점만.**
- 목표: "수동 30분 → 0분(E1·E2) + 스레드 1~3분(E3·E4)".
