# 0026 — 콘솔 어시스턴트에 문서 RAG 연결: 검색 전용 HTTP 서비스

- 상태: 채택(2026-08-04)
- 맥락: [ADR-0014](./0014-log-assistant.md)(로그 어시스턴트·근거번호 강제·동시 1) ·
  [ADR-0015](./0015-assistant-exploratory-query.md)(탐색형 질의계획) ·
  [ADR-0025](./0025-alert-relay-webhook.md)(alert-relay가 어시스턴트 응답의 두 번째 소비자) ·
  헌장 §11(에이전트 생성/사람 적용) · §12(라이브 직접수정 금지) · §13(시크릿 레포 밖) · §14(읽기 전용)
- 관련: `infra/rag/rag_service.py` · `apps/console/src/lib/rag.ts` · `infra/rag/README.md`

## 맥락

`infra/rag/`에 LightRAG 기반 문서 지식그래프가 이미 있다(문서 64 → 엔티티 351·관계 809,
egress 0). 그런데 그것을 쓰는 것은 CLI(`query.py`)뿐이고, 콘솔 어시스턴트는 여전히
OpenSearch BM25만 본다. 즉 **런북·ADR에 이미 적혀 있는 절차를 어시스턴트가 모른다.**

먼저 짚어야 할 것은 이 둘이 같은 것이 아니라는 점이다.

| | 답하는 질문 | 소스 |
| --- | --- | --- |
| BM25 로그 검색 | "이 에러가 **왜 났나**" | OpenSearch(관측된 사실) |
| 문서 RAG | "**매뉴얼이 뭐라 하나**" | 레포 마크다운(규정된 절차) |

그래서 이 결정은 **대체가 아니라 보강**이다. RAG가 BM25를 밀어내면 "지금 실제로 무슨
일이 일어났는가"를 잃는다 — 그건 어시스턴트의 존재 이유다.

## 결정

**LightRAG를 stdlib HTTP 서비스로 감싸 systemd로 띄우고(`127.0.0.1:8131`), 콘솔이 fetch한다.**
단, 서비스가 노출하는 것은 `aquery`(프로즈 생성)가 아니라 **`aquery_data`(구조화 검색)** 뿐이다.

이 결정의 핵심은 배선이 아니라 **LightRAG에 생성을 시키지 않는 것**이다. 답변 문장과
근거 번호는 콘솔이 계속 소유한다 — "서버가 검증한 번호만 렌더한다"(ADR-0014)는 계약이
그 소유권 위에 서 있기 때문이다. RAG가 프로즈를 만들면 검증되지 않은 인용이 콘솔을
우회해 화면에 오른다.

### 기각한 대안 (실측)

| 후보 | 기각 사유 |
| --- | --- |
| **(b) `child_process`로 `query.py` 실행** | 요청마다 **콜드 1.49s**(import 0.55s + 스토리지 로드 0.57~0.72s)가 고정 과세되고 색인 규모에 따라 선형으로 는다. Next 서버가 타임아웃·좀비·동시성을 직접 떠안고, 프로세스 내 LLM 키워드 캐시(warm 0.31s)를 못 쓴다 |
| **(c) `lightrag-server`** | `.venv/bin/lightrag-server`는 있으나 **fastapi·uvicorn·gunicorn 미설치**라 실행 불가(실측 `ModuleNotFoundError`). `lightrag-hku[api]` 설치 = egress + 의존성 30여 개. WebUI·인증·**문서 업로드/삭제 쓰기 엔드포인트**가 딸려와 읽기전용 콘솔 옆에 쓰기 관리면이 생긴다(§12·§14 위반). 질의 API도 생성 프로즈라 근거 구조가 없다 |

## 근거 합성 — 번호 공간을 나눈다

- **`[1]..[n]`** = 기존 BM25 `LogDoc[]`. **손대지 않는다.**
- **`[D1]..[Dm]`** = `data.chunks`. `file_path`는 `docs__runbooks__gpu-xid.md` 꼴이다
  (`ingest.py`가 `/`→`__`로 평탄화 — LightRAG 1.5.5가 file_path를 basename으로
  정규화해 중복 판정하는 것의 회피). 콘솔이 역매핑한 뒤 **레포에 실제 존재하는
  화이트리스트 경로만** 번호를 준다.
- 프롬프트는 `<<<DATA-LOGS>>>` / `<<<DATA-DOCS>>>` 두 블록으로 분리하고 "로그에서
  관측된 사실은 `[n]`, 문서가 규정한 절차는 `[Dn]`, 섞지 마라"를 지시한다.
  **문서 0건이면 빈 블록이 아니라 블록 자체를 생략한다** — "(문서 없음)"은 토큰만
  쓰고 모델에게 "찾아봤는데 없었다"는 잘못된 확신을 준다.

### 왜 로그 번호를 `[L n]`으로 바꾸지 않았나

설계 초안은 대칭을 위해 로그를 `[L1..Ln]`으로 바꾸려 했다. 실측에서 뒤집혔다:
`infra/alert-relay/alert_relay.py`의 `render_assistant_reply()`가 Slack 근거 목록을
**자기가 `[1] [2] …`로 결정적으로 렌더**하고, `test_alert_relay.py`의 AC-E3-7이
정규식 `\[\d+\]`로 그것을 판정한다. 콘솔만 `[L1]`로 바꾸면 Slack에서 본문 인용(`[L1]`)과
근거 목록(`[1]`)이 어긋난다. 관계된 유닛을 함께 고치면 라이브 알림 경로의 수용 기준을
건드리게 된다 — **문서 근거를 붙이려다 알림 경로를 흔드는 것은 값어치가 맞지 않는다.**

그래서 확장은 **가산으로만** 한다: 로그 번호는 그대로 두고 문서에 새 네임스페이스를
준다. 대신 문서 인용에는 경로를 함께 적게 해(`docs/runbooks/x.md [D1]`) 문서 목록이
없는 표면(Slack)에서도 `[D1]`이 무엇인지 문장만으로 읽히게 한다.

### `evidence`는 로그 전용으로 고정한다

같은 실측에서 나온 두 번째 결론이다. 문서 근거를 `AssistantAnswer.evidence`에 합치면
① 타임스탬프·노드·레벨이 없는 청크가 Slack에서 `None · None · None` 근거줄이 되고
② `render_assistant_reply()`의 **"근거 0건이면 답글 생략"** 안전장치가 문서 히트만으로
뚫린다. 문서는 새 필드 `docEvidence`로 간다.

## 실패 격리

RAG는 **없어도 되는 것**이다. 그 전제가 코드 전체에 박혀 있다:

- `retrieveDocs()`는 **절대 throw하지 않는다**. 거부·타임아웃·`status:failure`·검증
  탈락 전부 `{docs: [], status: "error"}`로 강등된다.
- `Promise.allSettled([searchLogs, retrieveDocs])` — BM25와 **병렬**이고, RAG의 reject가
  로그 검색을 끌고 내려가지 않는다. 반대로 로그 검색 실패는 지금까지처럼 throw다.
- `RAG_URL` 미설정이면 fetch 자체를 하지 않는다(`skipped`). `getRagUrl()`은
  `GLITCHTIP_DSN` 선례를 따라 **throw하지 않는다** — 부가 기능의 env 하나가 콘솔을
  못 뜨게 하는 실패는 이미 측정됐다(Grafana, 2026-07-30).
- UI는 `ragStatus:"error"`를 경고색 없이 한 줄로만 알린다. 사용자가 할 일이 없고
  답변 자체는 로그 근거로 이미 성립했기 때문이다.

## 예산

RAG는 BM25와 병렬이므로 순증은 `max(0, rag − bm25)`다. 프롬프트 증가는
4건×900자 ≈ +3~4K 토큰(컨텍스트 65536 여유). 동시성은 콘솔 `MAX_CONCURRENT=1`이
상류 게이트이고 서비스 세마포어 2는 이중 안전이다.

하드캡은 **4s로 잡았다가 6s로 올렸다**(`AbortSignal.timeout`, 서비스 쪽은 5.5s로
더 짧게 — 서버가 먼저 끊어야 코루틴이 정리된다). 라이브 실측이 이유다:

| 실측(2026-08-04, 콘솔 `/api/assistant` 경유) | 결과 |
| --- | --- |
| 신규 한국어 질문 3건, 키워드 없음(추출 LLM 포함) | 0.28s · 0.72s · 0.82s |
| 콘솔 첫 호출 1건 | **>3.5s → 504** |
| 같은 질문 재호출(warm) | 0.29~0.37s |

명시 키워드가 없으면 LightRAG가 키워드추출 LLM을 한 번 부르는데, 그 상대가
**공유 연구 GPU**라 지연이 우리 통제 밖이다. 4s에서 떨어진 그 1건은 답변 자체는
로그 근거 40건으로 정상이었지만(실패 격리가 설계대로 작동) 런북 근거를 통째로
잃었다 — 그건 이 기능을 만든 이유를 잃는 것이다. 6s는 통상값의 약 7배 여유이고,
그마저 넘으면 그때는 문서 근거를 포기하는 편이 맞다.

## 대가 · 한계 (정직하게)

- **운영 표면이 하나 는다.** systemd 유닛 하나, 포트 하나, 죽었는지 볼 것 하나.
  대신 external-watchdog에 물리지 않는다 — 없어도 되는 것을 감시하면 노이즈만 는다(§15).
- **색인은 사람이 갱신한다.** 문서가 바뀌면 `ingest.py` 후 `systemctl restart`(~0.7s).
  "재색인 트리거" 엔드포인트를 만들지 않는다(§11) — 그 순간 읽기전용이 아니게 된다.
- **엔티티·관계는 근거로 쓰지 않는다.** 실측에서 `entity.file_path`가 실제 출처가 아닌
  문서를 가리키는 사례가 있었다(동명 엔티티 병합의 부작용). 출처가 1:1로 붙는
  `chunks`만 `[D n]`으로 승격한다.
- **코퍼스가 커지면 부팅 시간·RSS가 선형으로 는다**(현재 351엔티티/278MB).
  `MemoryMax=1G`를 넘으면 그것 자체가 "청크 설정을 다시 볼 때"라는 신호다.
- **CI는 실물 LightRAG를 검증하지 못한다.** 러너에 venv·모델·색인이 없어서
  `test_rag_service.py`의 실물 `QueryParam` 계약 테스트는 스킵된다. 나머지 20건은
  가짜 RAG 주입으로 전부 돈다. 스킵이 통과로 보이는 구멍을 알고 남긴다 — 대안은
  CI에 GPU와 색인을 요구하는 것이고 그건 러너 원칙과 맞바꿀 수 없다.

## 불변 — 이 결정이 바꾸지 않는 것

조치 선택은 여전히 결정론이다(`remediation_l1.py`: frontmatter `alerts` 매칭 +
`actions` 화이트리스트, 적대검증 99회 주입으로 환각 차단 증명). **RAG는 진단·검색
계층이다.** 이 경계를 흐리는 변경 금지 — ADR-0025와 `infra/rag/README.md`가 같은 말을 한다.
