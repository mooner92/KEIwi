## 맥락 — 왜 자동화를 원하나, 그리고 왜 그 요청이 위험한가

요청은 한 문장이었다: **"로컬 LLM이 공식 매뉴얼을 참조해 어느 정도 해결까지 자동으로."**

이 요청에는 근거가 있다. 2026-08-03 첫 실전 알림(DiskUsageHigh · data04)에서 사람이 **30분 동안
df→du→find→소유자**를 손으로 따라갔다. 인프라 장애는 상당수가 정답형이다 — "Logstash가 설정을
못 찾으면 재시작한다"에는 판단의 여지가 없다. 런북에 이미 답이 적혀 있고, 사람은 그 문서를 열어
같은 명령을 복붙한다. **1인 운영에서 이 복붙은 MTTR의 대부분이 아니라 대부분의 *지연*이다** —
알림은 3분 만에 오는데 사람이 노트북을 여는 데 40분이 걸린다.

동시에 이 요청은 헌장 세 조항과 **정면으로 긴장한다**:

| 조항 | 요청과의 충돌 |
| --- | --- |
| §11 에이전트는 **생성**, 사람은 **적용** | "자동 해결"은 에이전트가 적용까지 하라는 뜻으로 읽힌다 |
| §12 라이브 직접수정 금지 | 조치는 정의상 라이브 상태 변경이다 |
| §I-1 온프레미스 · §14 인증=Cloudflare Access | 승인 UI를 외부 SaaS(Slack)에 두면 실행 권한이 사외 신원 체계로 나간다 |

그래서 이 결정은 "자동화를 할까 말까"가 아니라 **"어디까지가 헌장을 깨지 않고 갈 수 있는 최대치인가"**
를 정하는 결정이다. 그 최대치를 말하려면 공용 언어가 필요하고, 그것이 자율 사다리다.

## 결정

### 1. 자율 사다리 L0~L4를 이 프로젝트의 공용 언어로 채택한다

"자동 해결"이라는 모호한 요청을 **사다리에서 한두 칸 올라가는 것**으로 번역한다. 점프가 아니다.

| 레벨 | 이름 | LLM 권한 | 실행 주체 | 판정 |
| --- | --- | --- | --- | --- |
| **L0** | 진단만 | 읽기전용 · 근거번호 | 없음(사람이 다 함) | **라이브** — assistant · alert-enrichment |
| **L1** | 조치 **제안** | 닫힌 분류 → 런북 **선택** + 명령 블록 게시 | **사람이 복붙** | **채택 · 구현 완료** |
| **L2** | **승인 후 실행** | 위와 동일(제안까지) | 사람이 서버에서 `--apply` → **결정론 실행기** | **채택 · 구현 완료(파일럿 전)** |
| **L3** | 사전승인 **안전조치 자동** | 위와 동일(선택만) | 4조건 통과 화이트리스트만, 사람 클릭 없이 | **조건부 — ADR-0027(신설 예정) + 무사고 20회 뒤** |
| **L4** | 완전 자동 | 자유 진단 → 자유 조치 | LLM이 라이브에 직접 | **미채택 — 가지 않는다** |

각 칸의 경계는 문장이 아니라 **파일 경계**다. L1(`remediation_l1.py`)에는 실행 수단이 코드에
없고(게이트 L2가 문법 수준에서 강제), L2(`remediation_l2.py`)에만 `subprocess.run` 이 **정확히 한 번**
등장한다(게이트 M5). 사다리에서 한 칸 올라가는 일은 곧 **파일을 하나 더 만드는 일**이고, 그래서
"어느새 올라가 있었다"가 구조적으로 불가능하다.

### 2. L1(제안) 채택 — 이미 구현·검증 완료

LLM은 인시던트를 **닫힌 카테고리**로 분류하고, 그 카테고리를 담당한다고 선언한 런북에서
**이름 붙은 조치 하나를 고른다**. 명령 문자열은 **런북 파일에서 읽는다** — LLM 출력에서 오는 것은
`action_id` 라는 이름뿐이다. 실행 수단은 코드에 없다. 헌장 무충돌(순수 생성).

### 3. L2(승인 후 실행) 채택 — 단, 승인 경로는 **서버 CLI만**

사람이 서버에 로그인해 `remediation_l2.py approve <proposal_id> --apply` 를 친다. 그 순간
결정론 실행기가 **런북 파일을 다시 읽어** 그 조치의 명령을 실행한다.

핵심 계약 8개(전부 `check-remediation-l2.sh` 가 기계 검증):

1. **명령 문자열을 인자로 받지 않는다.** 실행기는 `proposal_id` 만 받고, 명령은 런북에서 다시 읽는다.
2. **드리프트 거부.** 제안 시점 런북 SHA-256 ≠ 실행 시점 SHA-256 이면 실행을 거부한다.
3. **`--dry-run`이 기본, `--apply`가 명시.** 인자 없이 부르면 아무것도 실행되지 않는다.
4. **거부 조건(fail-closed):** tier ≤ 1 · `risk: high` · `reversible: false` · `idempotent: false` ·
   파괴 동사 · 명령 치환(`$(`·백틱) · stale 런북 · 본문 미근거 명령.
5. **승인 없이는 실행 0.** 원장에 승인 이벤트가 없는 `proposal_id` 는 `--apply` 로도 실행되지 않는다.
6. **감사 원장 append-only.** 제안·승인·거부·dry-run·실행·rc·롤백 안내가 전부 남는다.
7. **데몬이 없다.** 리스너도, 타이머도, 큐도, 워커 루프도 없다. 사람이 명령을 치지 않으면
   실행을 기다리는 프로세스가 **존재하지 않는다**.
8. **멱등·타임아웃·rc 기록.** 같은 제안은 두 번 실행되지 않고, 각 명령은 타임아웃과 rc를 남긴다.

### 4. L3은 조건부 — 이 ADR로는 열리지 않는다

L3는 사람 클릭 없이 결정론 워커가 라이브를 바꾼다. 이건 **진짜 새 결정**이므로 별도
ADR-0027(신설 예정) + 후보별 "L2에서 무사고 20회"(earned autonomy) 뒤에만 연다. 그 전에는 **코드로 존재해서도
안 된다** — `check-remediation-l2.sh` 가 L2 모듈에 자동 트리거(타이머·데몬·webhook 리스너)가
들어오면 FAIL 시킨다.

## 근거

### 5-1. 벤치마크: "원인을 안다"와 "올바른 조치를 한다"는 다른 문제다

| 근거 | 수치 | 이 결정에 미친 영향 |
| --- | --- | --- |
| IBM **ITBench-SRE** | 최상 에이전트 인시던트 **해결률 13.8%** | 프론티어 모델도 7건 중 6건을 못 푼다 → 완전 자동(L4) 기각의 1차 근거 |
| **RAG 기반 RCA** 벤치 | 근본원인 정확도 91.4~99.7% vs **유효 복구 36.8~60.3%** | **정확히 이 간극이 L1과 L2를 가르는 선이다.** 원인은 맞혀도 조치는 절반이 틀리므로, 조치는 LLM이 짓지 않고 **사람이 쓴 런북에서 고른다** |

| MS **AIOpsLab** | 최고 에이전트 end-to-end **성공률 29%**, GPT-3.5+Shell은 가장 빠르지만(19초) **성공 0%** | "빠른 셸 접근 = 성공"이 아니다. 자유 셸을 주는 순간 속도만 오르고 성공률은 0이 된다 → L2가 자유 명령을 금지하는 근거 |
| Meta 실사용 RCA | 원인 top-5 정확도 42% | 세계 최고 인프라 팀도 LLM을 "실행"이 아니라 "후보 좁히기"에 쓴다 |
| **MicroRemed**(2025.11) | 다단계·정밀 파라미터 복구는 "비지도 배포 금지 수준" | L2를 **단일·멱등·가역 조치**로 좁힌 근거 |
| ReAct RCA(MS, 2024) | 정확도 35%지만 **검색 강제 시 환각 4~6%**(무근거 40% 대비) | 근거 없으면 제안 없음(§0-3)이 수치로 정당화된다 |

**우리 모델은 프론티어가 아니다.** 로컬 `:8003` Qwen3-Coder-30B는 BFCL-v2 76.63%로 "엄격 JSON 스키마가
주어진 단일 구조화 툴콜"엔 충분하지만 다단계 오케스트레이션은 상위 3~5개 모델만 신뢰 범주다.
**위 수치는 전부 프론티어 모델 기준이므로, 우리에게 적용할 때는 더 보수적으로 잡아야 한다.**

### 5-2. 업계가 수렴한 구조가 우리 헌장의 구현이다

PagerDuty(SRE Agent + Runbook Automation) · Datadog(Bits AI SRE) · Dynatrace(Davis+CoPilot) ·
Rootly · Resolve.ai · HolmesGPT가 **전부 같은 모양**이다:

> LLM = 읽기전용 진단·제안(비결정론) / 실행 = 사람이 미리 쓴 결정론 런북 / 그 사이 = 사람 승인 게이트.

LLM에게 프로덕션 명령을 자유 실행시키는 상용 제품은 사실상 없다. 반면
**k8sgpt-operator**는 `riskThreshold` 게이팅으로 자동 patch를 하면서 **롤백이 TODO**이고, 프로젝트가
스스로 "프로덕션 부적합"을 명시한다 — 반면교사다.

즉 §11(생성/적용 분리)은 우리만의 별난 제약이 아니라 **업계가 실패를 통해 도달한 결론과 같다.**

### 5-3. 5노드·1인이라는 규모가 상한을 더 낮춘다

- **1노드 = 플릿의 20%.** 한 번의 오조치 폭발반경이 곧 전 함대다. 수백 노드에서 "1노드 blast radius"가
  안전한 것과 5노드에서 같은 말을 하는 것은 전혀 다르다.
- **잡아줄 두 번째 엔지니어가 없다.** 오조치를 발견하는 사람과 저지른 사람이 같다.
- **연구 서버다.** `/home`·`/opt/conda/pkgs`는 재생성 캐시가 아니라 **남의 연구 데이터**다. 이 데이터에
  대한 조치는 영구 tier 0이고, 사다리에 오르지 않는다.
- 실측 분포가 이 상한을 확인해 준다 — 런북 16종 중 `t0=4 · t1=10 · t2=1 · t3=1`(2026-08-05).
  **88%가 제안 이하**이고, L2가 실제로 실행할 수 있는 것은 **런북 2편의 조치 7개**다.
  자동화 커버리지는 좁고, 좁은 것이 정직한 상한이다.

## 헌장과의 긴장을 어떻게 푸는가

### C1. "L2의 사람 클릭이 §11의 '사람이 적용'인가?" — 이 ADR의 핵심 논증

§11의 원문은 **"에이전트는 compose·config·스크립트를 레포에 생성한다. 프로덕션에 대한 실제 적용·
배포는 사람이 한다. 에이전트가 노드를 자율적으로 SSH-설치하지 않는다."** 이다.

이 조항이 금지하는 것을 정확히 읽으면 **주체**에 관한 규정이다 — *에이전트가 자율적으로* 적용하는 것.
L2에서 실제로 일어나는 일을 주체별로 분해하면:

| 단계 | 주체 | §11 판정 |
| --- | --- | --- |
| 조치를 **쓴다**(명령 문자열의 저작) | 사람 (런북 PR + 게이트 A1~A10 리뷰) | 생성 — 허용 |
| 조치를 **고른다**(어느 런북·어느 action_id) | LLM (닫힌 화이트리스트 안에서 이름만) | 생성 — 허용 |
| 조치를 **적용한다**(프로세스를 띄운다) | **사람** (서버에 로그인 → `--apply` 타이핑) | **적용 = 사람** |
| 적용의 **결과를 판정한다** | 사람 (원장 + rc + 스레드) | 사람 |

**에이전트가 자율적으로 실행을 개시하는 지점이 존재하지 않는다.** L2 실행기는 데몬이 아니다 —
리스너도 타이머도 큐도 없어서, 사람이 셸에 명령을 치지 않는 한 실행을 기다리는 프로세스 자체가
없다. 이것은 "사람이 승인 버튼을 눌러 워커를 깨우는" 구조보다 **한 단계 더 강한** 형태다:
승인과 실행 개시가 **같은 행위**다.

그래서 L2는 §11을 완화하는 것이 아니라, §11이 이미 허용하는 것의 **자동화된 준비**다.
사람이 하던 일은 "런북을 열고 → 명령을 찾고 → 복사하고 → 붙여넣고 → 엔터"였고, L2 이후에도
사람이 하는 일은 **여전히 엔터**다. 줄어든 것은 앞의 네 단계이고, 그 네 단계는 전부 §11이
말하는 "생성" 쪽이다.

> **반론과 답.** "그래도 사람이 명령의 내용을 안 보고 엔터만 치면 형해화 아닌가?"
> 맞다. 그것이 승인 피로(rubber-stamp)이고 실재하는 위험이다. 그래서 ① `--dry-run`이 기본이고
> ② dry-run이 **명령 전문·런북 경로·행번호·근거번호·위험도·롤백 안내를 전부 출력**하며
> ③ 그 dry-run 실행 자체가 원장에 남는다(**"보지 않고 승인했는가"가 사후에 드러난다**).
> 형해화를 없앨 수는 없지만, 형해화가 **기록되게** 만들 수는 있다.

### C2. "L3는?" — 이 ADR로 열지 않는다

L3는 사람 클릭 없이 라이브가 바뀌므로 위 논증이 통하지 않는다. **개정으로 뭉개지 않고**
별도 ADR-0027(신설 예정)로 정식 결정하며, 그때 헌장에 "L3 예외"의 경계(4조건 + 가드레일 + earned autonomy)를
ADR로 추가한다. 그 전까지 L3는 코드로 존재해서도 안 된다.

### C3. §I-1(온프레미스)·§14(인증=Cloudflare Access) — Slack 승인 버튼을 기각한 이유

→ 다음 절에서 별도로 다룬다. 이것이 이 ADR에서 스펙을 **뒤집은** 유일한 지점이다.

### C4. §13(시크릿 레포 밖) · §16(멱등성)

- 실행기는 자격증명을 갖지 않는다. 권한은 **실행하는 사람의 sudo**다 — 서비스 계정도 상주 토큰도
  없다. "워커가 root 권한을 갖게 된다"(README §C5)는 위험이 **설계에서 사라진다**.
- 실행 대상은 `idempotent: true` 인 조치로 제한하고, 같은 `proposal_id`의 재실행을 원장으로 막는다.

## 스펙을 뒤집은 판단 — Slack 인터랙티브 버튼 **미채택**, 서버 CLI 승인 채택

스펙 §3.3은 "1차: Slack 인터랙티브 버튼 / 폴백: CLI 승인"이라고 썼다. **이 ADR은 순서를 뒤집는다 —
CLI가 유일한 경로이고, Slack 버튼은 채택하지 않는다.**

### 무엇이 실제로 필요한가

Slack 인터랙티브 버튼은 **Slack이 우리에게 POST할 수 있는 공개 HTTPS 엔드포인트**를 요구한다
(Interactivity Request URL). 지금 이 망의 인바운드는 Cloudflare 터널 하나뿐이고, 레포 정책은
**"외부 진입 경로는 존재 자체를 알리지 않는다"** 이다(`check-public-safety.sh` P1이 도메인 문자열을
기계로 막는다). 즉 버튼 하나를 위해 **새 공개 엔드포인트를 여는 것이 정당한가**가 실제 질문이다.

### 공격 표면 vs 편의 — 정직한 저울질

| | Slack 버튼(공개 엔드포인트) | 서버 CLI(`--apply`) |
| --- | --- | --- |
| **인바운드 노출** | **새 공개 경로 1개.** 인터넷 전체가 도달 가능하고, 그 뒤에는 서명 검증 코드만 있다 | **0.** 새 리스너 없음 |
| **승인 권한의 소재** | Slack 워크스페이스 신원 = **사외 SaaS**. 워크스페이스 계정 탈취 → 프로덕션 실행 | 서버 SSH + sudo = **사내**. §14와 정합 |
| **취약점 표면** | 서명 검증(타이밍·재전송·`X-Slack-Retry`)·JSON 파싱·라우팅. 24/7 상시 노출 | 셸 로그인 경계(이미 존재·이미 감시) |
| **새 시크릿** | signing secret 1개 추가(§13) | 0 |
| **관측 대상 의존** | Cloudflare 터널은 data05에 있다. **data05 터널 런북을 승인하려면 그 터널이 살아 있어야 한다**(§C4 Facebook 2021) | 승인 경로가 관제 대상에 의존하지 않는다 |
| **속도(편의)** | 폰에서 3초 | 노트북 → SSH → 명령 = **분 단위** |
| **승인 피로** | **버튼은 피로를 만든다.** 카드를 안 읽고 누르는 비용이 0이다 | 타이핑이 마찰이고, 그 마찰이 읽게 만든다 |

**판단: 편의의 이득(분 → 초)이 상시 노출 인바운드 1개와 사외 신원 체계에 실행 권한을 위임하는
비용보다 작다.** 특히 결정적인 세 가지:

1. **비대칭성.** 인바운드 엔드포인트는 24시간 노출되지만 승인은 **한 달에 몇 번**이다.
   99.99%의 시간 동안 순수 위험이고 이득이 0인 자산이다.
2. **속도가 병목이 아니다.** L2 후보 조치(로그 수집기 재시작·위생 타이머 재기동)의 blast는
   **관측 평면에 한정**된다. 관측이 3분 늦게 복구되는 것과 프로덕션 실행 경로를 인터넷에
   여는 것은 저울이 성립하지 않는다. **속도가 중요한 조치는 애초에 L2가 아니라 L3의 문제다.**
3. **버튼은 승인 게이트의 품질을 낮춘다.** C1의 반론(형해화)에 대한 우리 방어는 "dry-run을
   읽게 만드는 마찰"인데, 폰의 버튼은 정확히 그 마찰을 제거한다. **편의가 곧 방어의 약화다.**

### 검토한 우회로와 기각 사유

| 대안 | 판정 |
| --- | --- |
| **Slack Socket Mode**(아웃바운드 WebSocket — 공개 엔드포인트 불필요) | 인바운드 문제는 실제로 푼다. 그러나 ① 상주 WebSocket = 상시 아웃바운드(ADR-0018의 egress 예외는 **1회성 HTTPS POST** 범위였다) ② app-level 토큰(`xapp-`) 새 시크릿 ③ **승인 권한이 Slack 신원에 있다는 본질은 그대로**다. ①③이 남으므로 기각. 다만 **인바운드 없이 버튼이 가능하다는 사실은 기록해 둔다** — 재검토 시 첫 후보다 |
| Cloudflare Access 뒤 승인 웹 UI | 인증은 §14와 정합하지만 여전히 인바운드 경로 + 새 앱 + 새 세션. 5노드·1인에 과잉 |
| Grafana 대시보드 버튼 | Grafana는 임의 명령 실행 수단이 없다. 있게 만들면 그것이 곧 새 실행 경로다 |
| 이메일 승인(회신 파싱) | 인바운드 필요 + 스푸핑 표면. 더 나쁘다 |

### 받아들이는 손실 (숨기지 않는다)

- **폰에서 승인할 수 없다.** 외출 중 장애는 **L2 이전과 똑같이** 사람이 접속해서 처리한다.
  L2의 이득은 "원격 승인"이 아니라 **"복붙 제거 + 드리프트 검증 + 감사 원장"**이다.
- **MTTR 단축 폭이 작아진다.** 우리가 사는 것은 속도가 아니라 **정확성과 추적성**이다.
- Slack은 계속 **단방향 통지 전용**이다(ADR-0018·0025 범위 그대로 — egress 예외를 넓히지 않는다).
  L2 제안이 스레드에 게시될 때 나가는 필드는 `slack_fields()` **한 함수**로 좁혀지고
  (alertname·severity·node·runbook_id·action_id·risk·proposal_id), `user`·`pid`·`cmdline`·`instance`는
  계약 테스트가 부재를 강제한다(AC-L2-5).

## 감사 원장을 OpenSearch가 아니라 **로컬 append-only 파일**에 두는 결정

스펙 §0-5는 "OpenSearch `keiwi-remediation-*`"이라고 썼다. 이 ADR은 **쓰기 경로를 로컬 파일로 두고,
OpenSearch는 파생 뷰로 남긴다**.

- **원장은 사고의 한복판에서 쓰인다.** L2의 1호 후보가 하필 **LogIngestStalled**(로그 인입 중단)이고
  2호가 **DiskUsageHigh**(디스크 풀)다. 로그 파이프라인이 죽어서 조치하는 순간에 그 조치의 감사
  기록을 **같은 로그 파이프라인으로** 보내는 것은 자기모순이다. ADR-0025가 "게시 전 sqlite 예약"을
  기각한 것과 **완전히 같은 논리**다.
- **1인 운영의 사후검증은 `cat` 으로 가능해야 한다.** JSONL 한 줄 = 한 사건이고, 도구 없이 읽힌다.
- **append-only가 파일에서는 O_APPEND + fsync 로 끝난다.** OpenSearch는 append-only가 아니다
  (문서를 지울 수 있다 — 감사 원장의 성질로는 더 약하다).
- **OpenSearch는 여전히 얻는다.** 원장 파일을 filebeat가 tail 하면 `keiwi-remediation-*` 인덱스가
  채워진다. 즉 **쓰기는 로컬(강한 보장), 조회는 OpenSearch(편의)**로 갈라진다. 이 배선은
  `[server]` 작업이라 코드만 두고 절차는 `infra/alert-relay/README.md`에 남긴다(§11).

받아들이는 손실: 노드가 통째로 죽으면 그 노드의 원장은 배송 전 구간만큼 잃는다. 완화는
filebeat 배송(기존 자산)이고, 완전한 해결은 아니다.

## 대안과 기각 사유

| 대안 | 기각 사유 |
| --- | --- |
| **A. 완전 자동(L4)** — LLM이 진단하고 바로 실행 | 위 벤치마크 전부가 반대한다(해결률 13.8% · end-to-end 29% · 환각 71%). 5노드에서 1노드 오조치 = 플릿 20%. 잡아줄 두 번째 사람이 없다. 헌장 §11·§12 정면 위배. **못 가는 게 아니라 안 가는 것이 올바른 설계 결정이다** |
| **B. 상용 SaaS 도입**(PagerDuty Automation · Datadog Bits AI · Rootly) | ① §I-1 온프레미스 위배 — 로그·메트릭을 사외로 보내야 조사 에이전트가 돈다 ② 5노드·1인 규모에 라이선스·운영 비용 과잉 ③ **그들이 하는 일의 구조가 이미 우리 것과 같다**(§5-2) — 사는 것은 UI와 통합이지 능력이 아니다 ④ egress 예외를 알림 1건에서 데이터 전면으로 넓힌다 |
| **C. 오픈소스 통짜 도입**(HolmesGPT/Robusta·k8sgpt-operator) | Holmes는 K8s 전제가 강하고 우리 플릿은 K8s가 아니다. k8sgpt-operator는 **롤백이 TODO**이고 스스로 프로덕션 부적합을 명시한다. **구조만 차용**하고 코드는 안 가져온다 |
| **D. 수동 유지(L0/L1에서 정지)** | 가장 안전하지만 요청에 답하지 않는다. 그리고 L1까지 온 지금, 남은 수동 작업은 "런북 열고 복붙"이라는 **가치 없는 마찰**이다. 더 중요하게 — **수동 실행은 감사 기록을 남기지 않는다.** 지금 누가 언제 무엇을 고쳤는지는 사람 기억에만 있다. L2는 속도보다 **추적성**을 산다 |
| **E. 스펙대로 Slack 버튼** | 위 저울질 참조. 공개 엔드포인트 + 사외 신원 + 승인 피로 |
| **F. 실행 워커를 데몬으로 상주** | 상주 프로세스는 "실행을 기다리는 것"이고, 그것이 있는 한 §11의 논증(C1)이 약해진다. 데몬이 없으면 사다리를 한 칸 잘못 올라갈 수단 자체가 없다 |
| **G. 명령을 인자로 받는 범용 실행기** | `remediation_l2.py --run "..."` 는 편리하지만 그 순간 이 파일은 **원격 셸**이 된다. 명령은 오직 런북 파일에서만 온다 |

## 결과 (예상 — 파일럿에서 실측으로 대체할 것)

- **L1(라이브 예정):** 알림 스레드에 근거번호 + 런북 명령 블록. 사람이 복붙. 실행 능력 0.
- **L2(파일럿 전):** `remediation_l2.py list` → `show <id>` → `approve <id>`(dry-run) →
  `approve <id> --apply`. 각 단계가 원장에 남는다.
- 대상은 오늘 기준 **런북 2편 · 조치 7개**(`log-ingestion-stopped` tier 3 · `node-hygiene-stale` tier 2).
  나머지 14편은 tier ≤ 1이라 L2가 건드릴 수 없다.
- 얻는 것: 복붙 제거 · **드리프트 검증**(런북이 바뀌었는데 옛 명령을 실행하는 사고 차단) ·
  **감사 원장**(누가·언제·무엇을·rc가 무엇이었나) · L3 승격의 근거 데이터(무사고 N회).
- 얻지 못하는 것: 원격 승인 · 큰 폭의 MTTR 단축 · 넓은 커버리지.

## 되돌리기 조건 (이 ADR의 유효기간)

다음 중 **하나라도** 성립하면 L2를 접고 L1(제안까지)로 되돌린다. 되돌리기는 파일 1개 삭제와
sudoers 항목 회수로 끝난다 — **데몬이 없으므로 중지할 서비스도 없다.**

1. L2 실행이 **원인이 되어** 장애를 만든 경우 **1건이라도**.
2. 드리프트·거부 로직이 **잘못 통과**시킨 사례 1건(거짓 음성). 거짓 양성(과잉 거부)은 되돌리기
   사유가 아니다 — 그쪽은 설계 의도다.
3. 승인 카드를 읽지 않은 `--apply`가 원장에서 반복 확인될 때(형해화 실증) — 그러면 마찰을
   **늘리는** 쪽으로 고치거나 L1로 되돌린다.
4. 유지 부담이 편익을 넘었을 때(1인 운영 기준: 한 달에 한 번 이상 손이 가면).

되돌린 이유·시각을 이 문서 하단에 남긴다. 남기지 않으면 다음 사람이 같은 실험을 반복한다.
