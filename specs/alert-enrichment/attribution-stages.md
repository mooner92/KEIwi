# 귀속 단계 게이트 — 0단계 다음은 자동이 아니다 (T-E4-8)

> 권위: [spec.md §4.3](./spec.md) · [README §2 게이트 표](./README.md). 이 문서는 그 게이트의 **판정 절차**를 명문화한다.
> 상태 2026-08-03: **0단계만 구현됨.** 1단계(psacct)·2단계(auditd/eBPF)는 **코드가 없고, 지금 만들지 않는다.**

---

## 0. 왜 문서가 따로 있나

"더 많이 수집하면 더 잘 안다"는 참이지만, 이 망에서는 그 대가가 **연구자의 명령어 이력**이다.
그래서 단계 상승을 기본값이 아니라 **관문**으로 둔다. 관문이 문서로 없으면 "일단 켜보자"가
기본값이 되고, 한 번 켠 수집은 잘 꺼지지 않는다.

이 문서는 세 가지를 고정한다: ① 각 단계가 무엇을 더 보는가 ② 올라가려면 무엇을 증명해야
하는가 ③ 판정을 누가 어떻게 기록하는가.

---

## 1. 단계 비교 — 무엇을 더 보고, 무엇을 더 잃나

| | **0단계 (현재)** | 1단계 psacct | 2단계 auditd 조사모드 / eBPF |
|---|---|---|---|
| 수집원 | df·du·find(read-only) + journald `COMMAND=` | 프로세스 계정(`lastcomm`·`sa`) | syscall 감사 규칙 / eBPF 프로브 |
| 보이는 것 | 파일 증거(누가 소유·언제·얼마나) + sudo 경유 명령 | **비sudo 포함** 실행된 명령 이름·계정·시각 | 명령 인자·파일 접근·네트워크까지 |
| 안 보이는 것 | 비sudo 명령, 파일을 안 남긴 활동 | **명령 인자**(미기록 — 프라이버시 장점) | (거의 없음) |
| 부하 | 알림 시 20초 내외(실측 data04) | CPU 1~2% 상시 | CPU 5~15% · 100MB~5GB+/일 |
| 프라이버시 비용 | 낮음 — 소유자·카테고리 | 중간 — 실행 이력 전량 | **높음 — 키로깅에 준함** |
| 상태 | **구현·검증 완료** | 미구현 | 미구현 |

> spec §4.1-4 불변: **키로깅성 수집(풀 auditd·bash history) 금지.** 2단계는 "상시 활성"이
> 아니라 **한시적 조사 모드**로만 존재할 수 있다.

## 2. 게이트 A — 0단계 → 1단계 (psacct)

### 질문
> **실사건 2건 이상에서 0단계 귀속이 불충분했나?**

"불충분"의 정의를 미리 못 박는다(사후 합리화 방지):

| 판정 | 조건 |
|---|---|
| **충분** | 수집기 출력만으로 "어느 계정의 어떤 성격의 작업인가"를 지목했고, 그 지목이 사후 확인에서 맞았다 |
| **불충분** | ① 원인 계정을 특정하지 못했다, **또는** ② 계정은 맞았으나 성격을 오판해 조치가 틀렸다 |
| **판정 보류** | 알림 자체가 오탐이었거나, 수집기가 partial 로 실패한 경우(→ 그건 수집기 버그로 따로 처리) |

### 통과 조건
- **불충분 사건이 2건 이상**이고, 두 건 모두 "비sudo 실행 이력이 있었다면 해결됐을 것"이라는
  구체적 근거가 있을 것. (파일 증거 자체가 없던 사건은 psacct 로도 안 풀린다 — 그건 3항 참조.)
- 2건은 **서로 다른 원인 유형**일 것. 같은 사람이 같은 실수를 두 번 한 것은 1건으로 센다.

### 판정 기록
`docs/runbooks/` 의 해당 사건 기록에 다음 4줄을 남긴다. 이 기록이 없으면 게이트는 미통과다.

```
사건: <날짜> <알림명> <노드>
0단계 출력 요약: <계정·카테고리·시각>
불충분 사유: <특정 실패 | 성격 오판> — <구체적으로 무엇을 몰랐나>
psacct 였다면: <어떤 레코드가 결론을 바꿨을 것인가>
```

### 통과 시 만들 것 (지금 만들지 않는다)
- `acct` 패키지 설치 role + `/var/log/account/pacct` 로테이션(디스크 사용량 상한 필수 —
  디스크 알림을 조사하려고 디스크를 채우는 자기모순 방지).
- 수집기에 `lastcomm --user <owner> --file <pacct>` 조회 모듈 추가. **반출은 여전히
  카테고리까지** — psacct 는 인자를 기록하지 않으므로 명령 이름조차 반출할지는 별도 판단.
- 노드별 옵트인. 전 노드 일괄 활성 금지.

### 되돌리기 조건
활성 후 8주 안에 psacct 레코드가 실제 사건 판정에 인용된 적이 0건이면 끈다.

## 3. 게이트 B — 1단계 → 2단계 (auditd 조사모드 / eBPF)

### 질문
> **psacct 로도 불충분했고, 성능·프라이버시 근거를 ADR 로 통과했나?**

### 통과 조건 (전부 충족)
1. 게이트 A 통과 후 **psacct 가 실제로 활성**인 상태에서, 그럼에도 원인을 못 짚은 사건 **1건 이상**.
2. **ADR 승인** — `docs/decisions/` 에 다음을 담아 작성하고 사람이 승인:
   - 무엇을 감사할 것인가(**전체가 아니라 특정 경로·syscall 한정**)
   - 활성 기간의 상한(예: 7일) 과 **자동 해제 방법**
   - 예상 디스크·CPU 비용과 그 상한을 넘을 때의 동작
   - 수집 데이터의 보존 기간·삭제 책임자
   - 대상자에게 알리는가(연구 노드의 사회적 계약)
3. **상시 활성 금지** — 조사 모드 종료가 코드/타이머로 보장될 것(사람의 기억에 의존 금지).

### 명시적 거부
- `execve` 전량 감사 · bash history 수집 · 키스트로크 · 네트워크 페이로드 — spec §4.1-4 위반.
  이 항목들은 게이트를 통과하더라도 **채택하지 않는다**(ADR 로도 뒤집지 않는다).

## 4. 게이트 어느 쪽도 아닌 실패 — 먼저 고칠 것

0단계가 "불충분"해 보이는 사건의 상당수는 단계 상승이 아니라 **0단계의 미완성** 때문이다.
게이트를 열기 전에 아래를 먼저 확인한다.

| 증상 | 진짜 원인 | 조치(단계 상승 아님) |
|---|---|---|
| 증가량을 모르겠다 | 베이스라인 미적재 | `keiwi-disk-baseline.timer` 활성(T-E4-6) |
| 창을 벗어난 파일이 원인이었다 | `--minutes` 기본 360이 짧았다 | 알림별 창 조정 |
| `partial: true` 로 반쪽 수집 | data05 `sudo -n` 불가 | hardware-ops T0-6 (**여기서 재정의 금지**) |
| 파일이 아예 안 남는 원인(로그 폭주·삭제된 열린 파일) | 파일시스템 증거의 사각 | OpenSearch 로그 검색·`lsof` 계열 별건 — psacct 로도 안 풀린다 |
| 계정은 맞는데 "무슨 작업인지" 모르겠다 | 카테고리 사전이 좁다 | `attribution_lib.categorize()` 패턴 추가(코드 3줄) |

## 5. 2주 리뷰에서 함께 볼 것 (spec §4.5)

- 계정명 반출이 실제로 문제를 일으켰는가(운영자 채널 전제가 유지되는가).
- 카테고리 4종이 실제 사건을 구분하기에 충분한가 — 부족하면 **단계를 올리기 전에 사전을 넓힌다**.
- "~로 보인다" 어조 계약이 지켜졌는가(LLM 요약이 단정한 사례 수).
