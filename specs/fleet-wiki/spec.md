# 플릿 지식 위키(fleet-wiki) — 서버·계정·프로젝트 문서 그래프

> 상태: **v2 — Q2·Q3·Q4·Q5 결정 반영(2026-08-13 사용자 리뷰). 남은 결정: Q1(서비스 분리 vs KEIwi 통합)**

> 발단: 사용자 아이디어 — *"열린 포트를 역추적해 디렉터리·git repo를 찾고, 서버·계정·프로젝트
> 단위 md 문서 그래프(LLM wiki)를 만들자. 서비스 탭 고도화이자 이상탐지·정합성의 기반."*

## 1. 목적 — 서비스 탭이 못 답하는 질문

서비스 탭(service-map v2.1)은 **"지금 무엇이 떠 있나"**(실시간 사실)를 답한다. 그러나 운영에서
실제로 던지는 질문은 그 다음이다:

- 이 포트의 프로세스는 **무슨 프로젝트**인가? 코드가 어디 살고, git은 어디에 연결돼 있나?
- 이 계정은 이 서버에서 **무엇을 몇 개** 운영 중인가? 마지막으로 손댄 게 언제인가?
- 새로 열린 이 포트는 **아는 것인가 모르는 것인가?** (이상탐지의 1차 질문)

지금 이 질문들의 답은 관리자의 기억과 `ss`/`ls` 수작업에 있다. fleet-wiki는 그 답을
**서버 → 계정 → 프로젝트 3계층 md 문서 그래프**로 만들고 콘솔에서 서빙한다.

**핵심 산출물은 "문서 없는 프로젝트의 문서"다**(사용자 결정 v2): git·README가 있는
프로젝트는 그것을 인용하면 되지만, 플릿의 상당수는 **둘 다 없는 채 포트만 열려 있다.**
그런 프로젝트에 위키가 README 수준의 정리본 md를 **대신 만들어** 한곳(`/wiki`)에 모아
보이게 하는 것 — 이것이 이 기능의 존재 이유다.

## 2. 문서 모델 — 3계층 + 정형 frontmatter

문서 규약은 검증된 LLM-wiki 패턴을 차용한다: **YAML frontmatter(기계용) + 본문(사람용) +
`[[위키링크]]`(그래프 간선) + 자동 색인 + lint**. 그래프의 간선은 임베딩이 아니라 명시적
링크다 — 결정론적으로 파싱·검증 가능하다.

```
servers/data03.md          ← 허브 노드(연결점 최다): 하드웨어·역할·운영 중 서비스 전체
accounts/data03--user2.md  ← 계정 노드: 권한 수준·운영 서비스 목록·활성 수·경로·최종 활동
projects/data03--user2--<project>.md ← 잎 노드: 포트·유닛·경로·git remote·README 요약
```

frontmatter는 **수집기가 관찰한 사실만** 담는다(사람 편집 금지 — 재생성 시 덮어씀).
본문 하단에 `<!-- manual -->` 구획을 두어 사람 주석은 보존한다.

```yaml
# projects/data03--user2--example.md
---
kind: project
node: data03
owner: user2            # OS 계정 (콘솔 표시용 — 외부 반출 없음)
ports: [8188]
unit: null              # systemd 유닛이면 이름, 세션 기동이면 null(= tmux 취약 신호)
cwd: /home/user2/…      # /proc/<pid>/cwd 실측
git_remote: <url|null>
git_head: <sha> (<날짜>)
readme: true
last_seen: 2026-08-13T02:00Z
first_seen: 2026-07-01T…
---
[[data03]] · [[data03--user2]]
## 무엇인가 (README 1줄 + LLM 요약은 P3)
```

## 3. 수집 파이프라인 — "포트에서 거꾸로"

핵심 아이디어 그대로: **열린 포트 → PID → cwd → git → README**. 기존 자산 위에 얹는다 —
port-exporter가 이미 포트↔프로세스↔PID↔소유자를 갖고 있고(ownership-attribution v1),
빠진 것은 **cwd·git 역추적**뿐이다.

| 단계 | 무엇 | 방식 |
|---|---|---|
| ① scout 수집기 | 노드별, **읽기 전용**: `ss -tlnp` → `/proc/<pid>/{cwd,exe,cmdline}` → uid→계정 → `git -C <cwd> remote/HEAD/log -1` → README·docs 목록 | port-exporter 패턴 복제(stdlib py, root, systemd timer 1h). **메트릭이 아니라 JSON 문서 출력** — 경로·URL은 Prometheus 라벨 카디널리티에 부적합 |
| ② 중앙화 | 노드별 JSON을 data05로 | **SSH pull 확정**(사용자 결정) — 기존 터널·키 경로 재사용, 노드에 새 자격증명·아웃바운드 0 |
| ③ 생성기 | JSON → md 3계층. **결정론·멱등**(내용 diff 시에만 재작성, `<!-- manual -->` 보존). 색인·고아·깨진 링크 lint 포함 | data05, cron |
| ④ LLM 보강 | README·docs·코드 트리 → 프로젝트 "무엇인가" 요약 | **칸반 증분 방식 확정**(§5.5) — 로컬 qwen3.5 9B, 네이티브 경로(think:false)로 요약 |
| ⑤ 그래프 | `[[링크]]` 결정론 파싱 → 노드·간선 JSON → `/graph`와 같은 임베드 문법으로 `/wiki` 그래프 뷰 | graphify 문서 모드는 LLM이 필요하므로 쓰지 않는다 — 위키는 간선이 이미 명시적이다 |

## 4. 저장 위치 — 레포에 넣을 수 없다 (설계 제약 1호)

위키 내용은 **실계정·홈 경로·프로젝트명**이다. 이 레포는 PUBLIC이고 게이트(P2·P3)가 정확히
그것들을 차단한다 — 즉 **위키 산출물은 이 레포에 커밋 불가능**하다(게이트가 막는 게 옳다).

v1(확정): `/data/keiwi/wiki/`(data05, 레포 밖) + 콘솔이 파일시스템에서 직접 읽기(코드 그래프
`CODE_GRAPH_PATH`와 동일 패턴). **이력 관리는 v1 범위 밖**(사용자 결정 — 생성기가 멱등이라
언제든 재생성 가능하고, 스냅샷 diff가 필요해지는 시점(이상탐지 P2)에 다시 판단한다).

## 5. 콘솔 통합 — 서비스 탭 고도화

- **포트 행 → 위키 링크**: `keiwi_listening_port_info`의 (node, port)가 위키 프로젝트
  문서와 매칭되면 행에서 문서로 진입. 매칭 실패면 —
- **"미등록" 배지 = 이상탐지 신호**: 위키에 없는 리스닝 포트는 형태로 드러낸다(점선 배지).
  "새 포트가 열렸는데 아무 문서도 없다"가 지금은 침묵이지만, 위키가 있으면 **기준선 대비
  diff**가 된다. orphan-port-holder 런북·alert-relay 보강의 컨텍스트 소스로도 쓴다.
- **`/wiki` 페이지**: 그래프 뷰(서버=허브) + 문서 뷰. 서버 렌더 — 클라이언트 상태에 걸지
  않는다(탭·테마 사고의 교훈).
- 어시스턴트: 위키 md를 LightRAG 코퍼스에 편입(P3) — "이 포트 뭐야?"에 문서 근거로 답한다.

## 5.5 요약 파이프라인 — 칸반 증분 (사용자 결정 v2)

9B급 소형 모델로 플릿 전체를 요약하는 방법은 **한 번에 다 읽는 게 아니라, 작게 잘라 오래
도는 것**이다(dev-booth에서 검증된 패턴: 컨텍스트가 차면 칸반에 중간 상태를 적고 이어간다).

- **칸반 = 큐 파일**(`/data/keiwi/wiki/.kanban.json`): 프로젝트 1건 = 카드 1장.
  상태 `todo → reading → summarized` + `stale`(git HEAD·mtime 변화 감지 시 재큐잉).
- **워커**: 카드 1장을 집어 README → docs → 파일 트리 순으로 **작은 청크**를 읽고, 중간
  요약을 카드에 적어가며(컨텍스트 리셋 내성) 최종 "무엇인가" 절을 만든다. ollama 네이티브
  `/api/chat` + `think:false`(lib/vllm.ts에서 검증된 경로)만 쓴다.
- **속도는 목표가 아니다** — 밤새 돌아도 되고 중단돼도 카드에서 재개한다. 시간당 카드
  수를 기록해 "전체 1회전에 며칠"을 측정 가능하게 한다.
- 산출은 문서의 `## 무엇인가` 절만 채운다 — frontmatter(관찰 사실)는 LLM이 못 건드린다.

## 5.6 정리본 md 템플릿 (사용자 결정 v2)

연구자에게 README 규약을 **배포하지 않는다**(코드 외부 노출을 장려하는 모양이 된다).
대신 **위키 생성기·요약 워커가 쓸 내부 템플릿**을 이 스펙에 둔다 —
[`templates/project.md`](./templates/project.md) · [`templates/account.md`](./templates/account.md) ·
[`templates/server.md`](./templates/server.md). 템플릿은 자리표시자만 담아 PUBLIC 레포에
안전하고, 실값이 채워진 산출물은 레포 밖(§4)에만 존재한다.

## 6. 무엇을 흡수·대체하나

- **sre-addons #5(경량 CMDB)**: owner·purpose 필드를 inventory에 넣자던 안 — fleet-wiki가
  상위 호환으로 흡수한다(inventory는 노드 SoT로 유지, 계정·프로젝트는 위키가 소유).
- 경로·문서 규칙(사용자 언급): 연구자에게 규약을 **강제하지도, 배포하지도 않는다**(Q4) —
  위키는 "관찰된 사실"을 적고, README가 있으면 인용하며, 없으면 §5.6 내부 템플릿으로
  정리본을 **대신 만든다.** 정돈은 위키 쪽 책임이다.

## 8. 결정 기록 (2026-08-13 사용자 리뷰)

- **Q1 → 재정의: 서비스 분리 vs KEIwi 통합** (유일한 미결). 판단 재료:

  | | KEIwi 안(모노레포) | 별도 서비스 |
  |---|---|---|
  | 재사용 | 수집기 패턴·SSH 경로·콘솔·게이트 전부 공짜 | 처음부터 구축 |
  | 결합 | 서비스 탭·이상탐지와 자연 결합 | API 경계 필요 |
  | 부담 | KEIwi 레포가 더 커짐 | 배포·관측 대상 +1 |

  **권고: v1은 KEIwi 안에서, 단 분리 가능하게** — 코드를 `infra/fleet-wiki/`에 격리하고
  산출물은 이미 레포 밖이므로, 나중에 디렉터리째 들어내면 분리가 된다. 지금 분리하면
  재사용 자산을 전부 다시 만든다.
- **Q2 확정: SSH pull** — 기존 터널·키 재사용, 노드에 새 자격증명·아웃바운드 0.
- **Q3 확정: 보류** — 세션·토큰 추적은 복잡하고 위험도가 높다(개인 활동 감시 소지).
  설계 기록만 남기고 **구현하지 않는다.** 재개하려면 대상자 합의가 선행 조건.
- **Q4 확정: 배포하지 않는 내부 템플릿** — 연구자용 README 규약 배포는 하지 않는다.
  템플릿은 위키 생성기·요약 워커 전용(§5.6).
- **Q5 확정: qwen3.5 9B + 칸반 증분**(§5.5) — 작은 컨텍스트로 천천히·꼼꼼하게. 별도
  모델 선정을 기다리지 않는다(네이티브 경로 요약 품질은 어시스턴트 실측으로 확인됨).
